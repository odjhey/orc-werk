# M4 — Cockpit & clarity

## Context, and the phase constraint

M3 closed "harden the loop." The product is thesis-complete — no missing
capability — so M4 is not a new-capability milestone; it is about **reach
and clarity** (operator direction, 2026-08-29): make orc usable across
projects, and make the operating roles crisp for whoever drives it.

**Hard constraint:** the project is deliberately in the **CLI-invocation /
incremental phase, and that is fine.** M4 is cockpit *ergonomics* and
*clarity* — NOT building automation to replace CLI invocation, NOT a
control-plane, NOT a daemon. Every M4 deliverable must stay in the
composition/CLI layer (`only orc_werk.cli composes adapters`,
`ARCH-REPOSITORY-STRUCTURE`), touch neither `core` nor `app`, add no
dependency, and preserve the no-framework / rung-1-install posture
(`PLAYBOOK-CLI-USAGE`, "No CLI framework, by design").

**Theme:** one place to see all your projects, one config you set once per
repo, and role guides so a watchtower and a work-doer each know exactly
what they do.

## The load-bearing architectural finding (shapes M4a + M4b)

Research (three recon passes, file:line-cited on the cards) established:
**no portfolio-level reporting exists today** — every reporting surface
(`orc report`/`--index`/`--all`, `orc show`, `orc refs`, bare `orc`) is
bounded to a single journal directory (`resolve_journal_dir` →
exactly one dir; the code's word "portfolio" means "all runs in one dir").
But **the shared Beads board is already the cross-project aggregator**:
every run mirrors into one `bd` workspace labeled `run:<run_id>`,
regardless of which project it came from — the mirror is *write-only*
(`INV-014`), so nothing on the orc read side consumes the board at
portfolio scope.

Consequence, and it is the spine of M4a/M4b: **the portfolio view is "read
the bd board back," not a new cross-journal-dir reader in orc.** The
cockpit is mostly (i) one small adapter change to add a `project:<name>`
label so the board slices by project, (ii) documenting the
bd-board-as-cockpit pattern (`bd list --label project:<name> --status
all`) reference-first, and (iii) a repo-default config so you stop
re-specifying per dispatch. Minimal new orc code; the board does the
aggregation, `bd`'s own CLI does the reading. orc reading bd state back
into a command would be a new posture against the write-only boundary and
is deliberately kept **out** (see "NOT in M4").

## Phase M4a — Multi-project cockpit

### `TASK-M4A-001` — repo-default config (named profile)
**The friction:** the dispatch config is strictly per-invocation; there is
no repo-level default, so an operator re-specifies (or must remember to
omit) `execution`/`candidate`/`assurance`/`mirror` on every dispatch of
every repo — the "remember to omit no-mistakes per repo" pain.
**Shape [SPECULATION]:** a repo-default profile — plain JSON, same schema
as the dispatch config, discovered by the CLI layer only. Least-surprising
insertion point (from the config recon): the `else` branch of
`cmd_dispatch` (`main.py:200-219`) where `config = {}` is chosen today; the
profile slots between the persisted per-run `config.json` and the `{}`
fallback, and an explicit `--config` **deep-merges over** the profile.
Effective precedence: **`--config` > per-run persisted config >
repo-default profile > `{}`**, with the existing `max_attempts`
sub-precedence intact beneath it. Reuse `config.py`'s `_validate_*`
functions as the gate — no schema/model refactor (config is a plain
`Mapping`). Honor the "no new config-FILE surface" posture consciously:
this IS the first repo-level config-file discovery in the CLI, so its
location + discovery rule needs an explicit operator ruling (see Open
questions). `orc onboard` gains a step to write it idempotently under its
existing never-clobber/`--force` discipline (staying pure scaffolding —
never touches a journal).
**Scope honesty:** new code (a loader + a merge point + an onboard step),
all in `cli/`. No core/app/adapter change.

### `TASK-M4A-002` — `project:` label for board slicing
**The bottleneck:** the shared board is sliceable by *run* today
(`bd list --label run:<id>`, already generated by `refs.py`), but there is
**no `project:` label anywhere** — so "what's in flight in project X" is
unanswerable on the board.
**Shape:** add an optional `project` to the `mirror` config block; plumb it
to `BeadsMirror` and emit a second `--label project:<name>` pair at
`_create_work` (the one place `--label` is applied). ~5 lines of adapter +
config: `_MIRROR_CONFIG_KEYS` gains `project`, the mirror-config validator
accepts it, `build_mirror` forwards it, `_create_work` appends the label
pair. Because create is an upsert re-issued every dispatch, existing issues
gain the label on the next run — no backfill. Amend
`ADAPTER-BEADS-MAPPING`'s label-discipline + operation-mapping rows.
**Scope honesty:** small new code (one label dimension) + docs. The
adapter stays write-only.

### `TASK-M4A-003` — the portfolio-cockpit pattern (docs, reference-first)
**Shape:** document the bd-board-as-cockpit pattern as the sanctioned
cross-project view: one shared `bd` workspace + `ORC_JOURNAL_DIR` per
project (formalize the M3 dormant "shared-portfolio convention" now that
its trigger fired) + the `project:`/`run:` label slices. The reading is
`bd`'s own CLI (`bd list --label project:X --status all`, grouped by
`run:`), NOT a new orc command — reference-first, and it respects the
write-only boundary. `orc onboard`'s verification step notes the portfolio
workspace. Update `PRODUCT-ADOPTION` (this is the multi-repo rung).
**Scope honesty:** docs + convention formalization; no new orc read code.

### `TASK-M4A-004` — mode-aware agents-block
**The gap (operator, 2026-08-30):** onboarding agents in a repo that uses
orc WITHOUT the acp/no-mistakes adapters still requires a hand-written
preamble ("orc runs in scripted mode here; you do the work and record
settlements by hand"). M4A-001's profile closes the *config* half (scripted
becomes the default); this closes the *mode-declaration* half.
**Shape:** `orc onboard` DERIVES the mode from `.orc/profile.json`'s adapter
config (scripted/absent adapters → scripted mode; `acp`/`no-mistakes` →
adapter-driven) and writes a mode declaration into the agents-block it
already installs — generated, accurate, idempotent, pointing at
`orc guide <role>`. Retires the hand-written preamble. Ties `TASK-M4A-001`
(writes profile) to `TASK-M4C-001` (the guide).
**Scope honesty:** CLI-layer scaffolding + docs; no adapter/core change; the
mode is descriptive (derived from config), not a new runtime gate.

## Phase M4b — Clearer reporting

Portfolio-level reporting is delivered by M4a (read the board). M4b is the
**per-dir / per-run polish** the recon flagged as "mechanics already
present," plus one honest gap.

### `TASK-M4B-001` — richer single-dir index
**Shape:** the bare-`orc` index and HTML `--index` gain state-aware views —
blocked-first / non-terminal-first sort, filter by state, per-work rollups
— extending `cmd_index`/`_index_run_line` and `render_index` (pagination
and per-row degradation already exist). Also **unify the ordering
inconsistency** the recon found: bare `orc` sorts by file mtime, HTML
`--index` by discovery/id order — pick one and make them agree.
**Scope honesty:** polish of existing surfaces; no new surface.

### `TASK-M4B-002` — cross-run rollup within a dir — FOLDED into M4B-001
**Decision (watchtower, 2026-08-30): FOLD — delivered by subsumption, no
separate surface.** The card asked us to decide standalone-vs-fold once
M4B-001 shipped. It shipped, and M4B-001's `--state active` filter plus the
per-run `states=<counts> flags=blocked,pending` rollup already *is* the
in-flight roll-up over one journal dir this card described — all
non-terminal / blocked works at a glance, with blocked reasons. Verified
live on merged master:

```
$ orc --state active
4 runs in .../.orc:
trivia-sweep: states=READY:1 | sweep=READY attempts=2
fix-71-corpus: states=BLOCKED:1 flags=blocked | work-1=BLOCKED attempts=3 blocked_reason=retry-budget-exhausted
...
```

`_summarize_states` graduated from per-run-only into the shared
`_index_state_rollup` helper (report.py) that both index surfaces consume,
which was the mechanics gap this card named. A separate standalone surface
would duplicate that with no added information.
**Deferred nicety (not pulled):** a single dir-level aggregate header
(e.g. "4 runs — 2 blocked, 2 ready") above the default (unfiltered) list.
Marginal — the per-run flags already make blocked obvious and `--state
active` already isolates in-flight — so it stays a follow-up pulled only if
friction calls for it, not a milestone item.
**Scope honesty:** no new code; a decision record. M4b is complete with
M4B-001 alone.

## Phase M4c — Role guides (the clarity the operator asked for)

The operating roles — **watchtower** (coordinator), **shipper / work-doer**,
**verify seat** — are real and used every session, but their guidance is
scattered across dense docs (`PLAYBOOK-WATCHTOWER`, `PLAYBOOK-AGENT-CLI`,
`DELIVERY-STANCE`). M4c distills crisp, actionable, per-role guides.

### `TASK-M4C-001` — the three role guides
**Shape:** three short guides, each answering "if you are this role, here
is exactly what you do":
- **Watchtower guide** — decompose; dispatch with zero ambiguity; verify
  adversarially; merge; record. Distilled from `PLAYBOOK-WATCHTOWER`.
- **Shipper / work-doer guide** — claim; implement; stop-and-report on
  ambiguity; record your settlement + candidate (never your own verdict).
  Distilled from `PLAYBOOK-AGENT-CLI`'s seat discipline.
- **Verify-seat guide** — derive identity independently; adversarial
  probes; findings ride the verdict entry's `extensions`; never
  self-assure.
The `orc-ledger` skill stays the six-rule quickstart; these guides are the
**depth** each role reaches for. Per operator ruling (2026-08-30): `orc guide` is HELD dormant (see `TASK-M4C-001`). Role clarity is instead covered by three existing surfaces — the installed `orc-ledger` skill (durable principles), the per-project mode declaration (`TASK-M4A-004`), and `PLAYBOOK-AGENT-CLI` (full reference). The canonical command is pulled only if a proven gap remains.
**Scope honesty:** the guide content is docs (distilled from the dense
playbooks); the `orc guide` command is small new CLI code (reads a packaged
doc and prints it, like config-schema).

## Sequencing

M4a first (the cockpit the operator prioritized): M4A-002 (`project:`
label) and M4A-001 (repo-default config) are independent and can run in
parallel; M4A-003 (docs) depends on both landing. M4b follows (polish;
M4B-001 before deciding M4B-002). M4c can run in parallel with either — it
is docs — but reads best authored after M4a so the guides reference the
cockpit. The whole milestone is small and mostly composition-layer/docs.

## Rulings (operator, 2026-08-30)

1. **Repo-default profile location: `.orc/profile.json`** — RULED. Plain
   JSON, same schema as the dispatch config, discovered by the CLI layer
   only (the first config-file-discovery surface; kept minimal, no
   framework).
2. **`--config` deep-merges over the profile** — RULED. Profile provides
   defaults; `--config` overrides keys; they compose. Precedence:
   `--config` (merged) > per-run persisted config > `.orc/profile.json` >
   `{}`, with the `max_attempts` sub-precedence intact beneath.
3. **Portfolio view: convention + docs only** — RULED. Raw `bd list --label
   project:<name> --status all`, reference-first; no new orc read command
   (respects the write-only boundary; a board-reading command stays dormant
   in the multi-repo registry).
4. **Role guides: `orc guide` HELD dormant** — RULED (operator, 2026-08-30, supersedes the earlier `orc guide` decision). The command sits in a possibly-redundant middle; role clarity is covered by the installed skill (principles) + the per-project mode declaration `TASK-M4A-004` (procedure) + `PLAYBOOK-AGENT-CLI` (reference). `orc guide` is dormant with a named trigger (`TASK-M4C-001`): agents demonstrably getting seat discipline wrong despite those three surfaces.
5. **`project:<name>` source: explicit `mirror.project` config key** —
   RULED, set once in `.orc/profile.json` (ties M4A-001 and M4A-002).
6. **`TASK-M4B-002` folds into M4B-001** — RULED (watchtower, 2026-08-30).
   M4B-001's `--state active` filter + the shared `_index_state_rollup`
   helper are the single-dir in-flight roll-up M4B-002 scoped; a standalone
   surface would only duplicate it. The dir-level aggregate header is a
   deferred nicety, not a milestone item. **M4b is complete.**

## Acceptance

- A repo sets its execution/candidate/assurance/mirror defaults ONCE (the
  profile) and dispatches without re-specifying them; `--config` still
  overrides.
- `orc onboard` writes a mode declaration derived from the profile, so a
  scripted-only repo no longer needs a hand-written "scripted mode" preamble
  (M4A-004).
- The shared board answers "what's in flight in project X" via a
  `project:` label slice (`bd list --label project:X --status all`).
- The single-dir index is state-aware and text/HTML orderings agree.
- A watchtower, a shipper, and a verify seat each have a crisp guide that
  tells them exactly what to do, reachable by a fresh agent in an adopting
  project.
- No `core`/`app` change; no new dependency; the write-only mirror boundary
  intact.
